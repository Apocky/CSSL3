The encrypted desktop bridge reuses the existing `chat_session` and `chat_turn` tables. It does not require an inbound port, a new DNS route, or a new service provider. The website admits requests from its existing verified account or owner routes; the desktop worker polls outward over HTTPS.

Only server code may call `fetchBridge`. Supply the already verified Supabase user UUID, the channel, exact allowed runtime target and request bytes. Owner requests must match the configured owner UUID. A request body cannot select another account, a different URL, or an owner credential. The desktop worker supplies its local runtime credentials; these are never stored in the queue.

The server requires all four environment values: `APOCRYPHA_BRIDGE_KEY_B64` (a canonical base64-encoded 32-byte random key), `APOCRYPHA_BRIDGE_KEY_ID`, `APOCRYPHA_BRIDGE_WORKER_ID`, and `APOCRYPHA_BRIDGE_OWNER_USER_ID`. It also uses the existing server-side Supabase service client. Configure the matching bridge key and identifiers through the worker's protected configuration channel. Never put these values in public environment variables, browser storage, source control, logs, or chat. Deployment and environment activation are separate operator steps.

Requests and responses use separate HKDF-derived AES-256-GCM keys. A signed node index admits jobs, because the inherited table policies permit users to insert their own queued rows. The worker never scans arbitrary queued rows. Every admitted row also checks its authenticated ciphertext, job identity, user and session ownership. Deleted or invalid rows are removed from the admission index without execution. The server stores only encrypted payloads and private operational metadata; request prompts use a fixed placeholder and response columns stay empty.

Authentication MACs bind the worker identity, exact method/path/body, timestamp and nonce. A signed compare-and-swap node record stores replay nonces across server instances. Queue leases and completions use row revision and status compare-and-swap. A lost completion acknowledgment can be retried with exactly the same lease and encrypted result. A stale or mismatched lease cannot replace a result.

The admission lifetime is ten minutes and a lease lasts seven minutes. Jobs accept at most 262,144 request bytes and 2 MiB of response bytes. Polling returns one encrypted job. An aborted HTTP request or a 504 response does not cancel a job that may already have started. POST jobs preserve their runtime request or operation ID; renewed leases reuse the exact request. Only the allowlisted runtime routes with durable idempotence are eligible. Code operations that the runtime records as indeterminate must be inspected there, not silently restarted.

There are at most 128 pending admissions per node and eight per account. The shared node record deliberately favors a single desktop worker. Completed encrypted rows remain available for exact-request readback and protected operator correlation; this implementation does not introduce a retention deletion job. Drain pending work before changing the bridge key or worker identity. Preserve the previous configuration until the operator verifies the new path; key rotation does not decrypt or migrate old queue rows.
